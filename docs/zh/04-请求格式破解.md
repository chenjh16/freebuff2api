# 请求格式破解：免费模式 CLI 网关机制

> 本文是本次逆向分析最重要的成果。它解释了为什么普通的 OpenAI 请求会被
> 上游拒绝（`403 free_mode_cli_required`），以及正确的请求格式是什么。

## 问题现象

代理实现的请求流程本身没问题（会话创建、Agent 运行都能成功），但
`POST /api/v1/chat/completions` 总是返回：

```json
{
  "error": "free_mode_cli_required",
  "message": "Free mode is only available through the freebuff CLI. Install it with `npm i -g freebuff`, then run `freebuff`. Calling the API directly is not supported and may get your account banned."
}
```

也就是说，免费模式有一个 **CLI 网关**：它要确认请求确实来自官方 CLI，
否则拒绝并警告可能封号。

## 研究方法

### 1. MITM 抓包（得到"标准答案"）

我们编写了 TLS 中间人代理（`tools/mitm-ssl-proxy.mjs`），让官方 CLI
（`freebuff` v0.0.141）通过该代理访问 `www.codebuff.com`，捕获了它发出的
**成功**请求（HTTP 200 + SSE 流）：

- 请求头 `User-Agent: ai-sdk/openai-compatible/0.0.0-test/codebuff ai-sdk/provider-utils/3.0.25 runtime/browser`
- 请求体包含：`model`、`stop`、`codebuff_metadata`、`provider`、
  **3 条 messages（system + 2 条 user）**、24 个 tools、`tool_choice`、`stream`

捕获的请求体保存为 `tools/captured/chatbody-official.json`，Agent 定义
（`/api/agents/validate` 发送的 460KB payload）保存为
`tools/captured/agentdefs-full.json`。

### 2. 变体二分（确定哪些字段是必须的）

我们写了一个二分脚本（`tools/discover-gate.mjs`），逐个关掉请求体中的
某个字段（system 消息、tools、stop、provider 等），用真实账号实时打上游，
观察网关放行还是拒绝。

## 测试结果表

| 变体 | system 消息内容 | 结果 |
| ---- | --------------- | ---- |
| EXACT-FULL | 官方完整 system 提示（10,788 字符） | ✅ 200 SSE |
| SHORT-BUFFY | `You are Buffy, the strategic coding assistant. You are the AI agent behind the product, Freebuff, a tool where users can chat with you to code with AI for free.` | ✅ 200 |
| FIRST-SENTENCE | `You are Buffy, the strategic coding assistant.` | ✅ 200 |
| NO-TOOLS | 同 EXACT，但去掉 tools | ✅ 200 |
| NO-STOP | 同 EXACT，但去掉 stop | ✅ 200 |
| NO-PROVIDER | 同 EXACT，但去掉 provider | ✅ 200 |
| EXACT-OUR-UA | 用代理自己的 UA（`0.10.7` 版本） | ✅ 200 |
| NO-SYSTEM | 完全没有 system 消息 | ❌ 403 |
| MINIMAL-FULL | `You are a helpful assistant.` | ❌ 403 |
| BUFFY-NAME | `You are Buffy.` | ❌ 403 |
| FREEBUFF-ONLY | `You are an AI assistant for the product Freebuff.` | ❌ 403 |
| BUFFY+FREEBUFF | `You are Buffy. You are the AI agent behind the product Freebuff.` | ❌ 403 |
| CLI-MARKER | `You are the official freebuff CLI coding assistant.` | ❌ 403 |

## 核心结论

**免费模式网关检查的是 system 消息中的精确短语：**

```
You are Buffy, the strategic coding assistant
```

- 只要 messages 里有一条 system 消息包含该短语 → **放行**（HTTP 200）
- 否则 → `403 free_mode_cli_required`
- 其余字段（tools、stop、provider、user-agent 版本号、完整 system 内容）
  均 **可选**，不影响网关判定

这也解释了为什么此前的尝试全部失败：`scratch-e2e.mjs` 的 baseline 请求只有
一条 `{role: "user"}` 消息，没有 system 消息；`scratch-replay.mjs` 的各种
system 变体（"You are a helpful assistant"、纯名字、大小写转换等）都不含
目标短语。

## 修复实现

`src/handler.ts` 新增 `injectCliSystemMarker()`，在转发前保证 system 消息
携带该短语：

1. 若某条 system 消息已包含目标短语 → 不做任何改动
2. 否则若存在第一条 system 消息 → 把标记**合并**到其前面
   （保留客户端自己的 system 提示）
3. 否则 → 在 messages 最前面**插入**一条独立 system 消息

```ts
const CLI_SYSTEM_MARKER =
  "You are Buffy, the strategic coding assistant. " +
  "You are the AI agent behind the product, Freebuff, " +
  "a tool where users can chat with you to code with AI for free.";
```

这样任何 OpenAI 客户端（Claude Code、Cline、curl…）都不需要知道这个
网关细节，代理自动注入。

## 修复后的端到端验证

```bash
curl http://127.0.0.1:23333/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"freebuff/deepseek/deepseek-v4-flash","messages":[{"role":"user","content":"Reply with exactly: PONG"}]}'
```

- ✅ 流式（`stream: true`）：HTTP 200，SSE 正常推送 `chat.completion.chunk`
- ✅ 非流式：HTTP 200，返回真实回复 `"content":"PONG"`，带 usage 统计
- ✅ 代理日志确认上游请求体已注入 system 标记、`ancestorRunIds: []` 等

## 其他顺带发现

- `free_mode_invalid_agent_hierarchy`：曾在 system 变体通过网关后出现，
  提示 Agent 层次问题——run 的 `agentId` 必须与 session 的 model 匹配
  （`base2-free-deepseek-flash` ↔ `deepseek/deepseek-v4-flash`）。
- 官方 CLI 的 `agent-runs` START body 是
  `{"action":"START","agentId":"…","ancestorRunIds":[]}`，
  代理已按此对齐（`src/upstream.ts`）。
