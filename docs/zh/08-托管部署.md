# 08 — 托管部署（Freebuff）

## 为什么是 Next.js？

核心代理是一个独立的 Bun/Node 服务器（`src/index.ts`）。Freebuff 托管只
构建 **React 系项目**（Vite + React、Next.js、Create React App），因此为了
免 VPS 部署，仓库额外内置了一个 Next.js App Router 应用（`app/`），把
**完全相同的**请求处理器（`src/handler.ts`）挂到标准 OpenAI 接口后面。

```
┌─────────────────────────── 托管应用（Next.js） ────────────────────────────┐
│  GET  /healthz               →  ┐                                          │
│  GET  /v1/models             →  │  app/lib/proxy.ts（惰性单例）            │
│  POST /v1/chat/completions   →  ┘  ├─ loadConfig()                        │
│                                    ├─ ModelRegistry（免费 Agent 映射）     │
│                                    ├─ TokenManager（免费会话）             │
│                                    ├─ RunManager（Agent 运行）             │
│                                    └─ createHandler()（来自 src/handler.ts）│
└────────────────────────────────────────────────────────────────────────────┘
```

同一份代码路径意味着本地 CLI 服务器与托管端点行为完全一致（会话准入、
503 等待室、模型锁定、流式、CLI 网关 system 标记注入）。

## 公开接口

- **域名：** `https://open.freebuff.app`
- **Base URL：** `https://open.freebuff.app/v1`

| 方法 | 路径 | 说明 |
| ---- | ---- | ---- |
| GET | `/` | 落地页：登录、API Key 管理、模型测试 |
| GET | `/healthz` | 公开存活状态 |
| GET | `/v1/models` | 当前可用的免费模型 |
| POST | `/v1/chat/completions` | Chat —— JSON 或 SSE 流式 |
| POST | `/api/auth/start` | 发起设备码登录（网页） |
| GET | `/api/auth/status` | 轮询登录状态直到用户完成登录 |
| POST | `/api/auth/register` | 校验账号 token 并签发 `sk-fb-…` key |
| POST | `/api/auth/revoke` | 吊销 API key（退出登录） |
| POST | `/api/gate/verify` | 校验站点访问 token（开启门禁时用于解锁控制台） |

API 鉴权方式为 `Authorization: Bearer <key>` 或 `x-api-key: <key>`。

## 部署环境变量

| 变量 | 必需 | 默认值 | 说明 |
| ---- | ---- | ------ | ---- |
| `AUTH_TOKENS` | 否 | 登录保存的凭证（仅独立 CLI） | 共享 Freebuff auth token（逗号分隔）。网页登录模式可不设置；需要共享 token 池时再配置。 |
| `PROXY_SECRET` | 否 | 自动 | 加密网页登录 API Key（`sk-fb-…`）的稳定密钥。设置固定值可让 key 跨重新部署保持有效。 |
| `API_KEYS` | 否 | 空（fail closed） | 客户端必须携带的显式高熵 key。托管 `/v1` 未配置前拒绝请求，避免公开可预测凭据。 |
| `SITE_ACCESS_TOKEN` | 否 | — | 网页控制台门禁 token（逗号分隔）。设置后访客必须提供其中一个（锁屏输入，或 `?token=…`）才能解锁站点。 |
| `UPSTREAM_BASE_URL` | 否 | `https://www.codebuff.com` | Freebuff 后端地址。 |
| `REQUEST_TIMEOUT` | 否 | `15m` | 上游请求超时。 |
| `ROTATION_INTERVAL` | 否 | `6h` | Agent run 轮换间隔。 |
| `MAX_BODY_SIZE` | 否 | `16MB` | Chat 请求体上限。 |
| `MAX_CONCURRENT_REQUESTS` | 否 | `32` | 最大并发 chat 请求数。 |

与
[07-配置与使用](07-配置与使用.md) 中的变量一致；托管应用从部署环境读取。

## 网页登录（每个用户独立的 API Key）

除了共享的 `AUTH_TOKENS` 池，访客也可以直接在网页上登录（流程与
`freebuff2api login` 一致）：

1. 页面请求一次性设备码链接（`POST /api/auth/start`），新标签页打开并轮询
   `GET /api/auth/status`，直到用户在 freebuff.com 完成登录。
2. 服务端轮询上游并把账号 token 保存在短期、绑定 HttpOnly Cookie 的登录
   事务中；浏览器不会收到原始 token。注册时服务端用 `GET /api/v1/me` 校验，
   再签发 `sk-fb-…` 格式的 API Key（AES-256-GCM 加密）。
3. 代理每次请求都把 `sk-fb-…` key 解密回账号 token 使用，所以任何
   OpenAI 兼容客户端只需携带 API Key；每个 key 的会话/额度归属各自账号。
4. 页面上的**退出登录**会在当前服务器进程内吊销该 key，并清除浏览器本地副本；
   再次登录会签发新 key。由于托管实例可能是临时的或水平扩展的，吊销状态不会跨实例持久同步；如果需要持久吊销，应接入真正的共享状态存储。

因此托管模式下 `AUTH_TOKENS` 是**可选的**：它只供默认 `API_KEYS` 使用共享
池。key 加密密钥的派生顺序：`PROXY_SECRET`（推荐，固定值可让网页登录的
key 在重新部署后仍然有效）→ `AUTH_TOKENS` 的哈希 → 本地文件持久化密钥
（`.data/proxy-secret`，无环境变量时 key 也能跨进程重启保持有效）→ 进程
随机（重启后 key 失效）。在无服务器或多实例托管中请显式设置 `PROXY_SECRET`；本地文件不是共享部署存储。

## 站点访问门禁（可选）

默认任何人都能打开控制台。若想限制站点使用者，在部署环境设置
`SITE_ACCESS_TOKEN`（支持逗号分隔的多个 token）。此后页面会显示锁屏：

- 访客在锁屏输入 token，或直接用带 token 的 URL 打开站点：
  `https://open.freebuff.app/?token=…`
- `POST /api/gate/verify` 负责校验（SHA-256 恒定时间比较，防时序侧信道），
  返回 `{ok: true}` 或 `401`。
- 验证通过后浏览器把 token 存在 `localStorage`，每次访问重新校验——刷新
  页面不会再次要求输入。
- 无效的 `?token=…` 会从 URL 中移除，并显示锁屏与错误提示。

> 门禁只是控制台的**前门**。`/v1` 接口无论是否开启门禁，始终由
> `API_KEYS` 保护。未设置 `SITE_ACCESS_TOKEN` 时控制台行为与之前完全
> 一致（开放）。

> ⚠️ **`AUTH_TOKENS` ≠ `API_KEYS`**——两者是不同凭据。`AUTH_TOKENS` 是你的
> **freebuff.com 账号 token**（用 `freebuff2api login` 获取，或来自你在
> freebuff.com 上的浏览器会话）；`API_KEYS` 是**你的客户端**通过
> `Authorization: Bearer` 携带的显式客户端 key；托管未配置 `API_KEYS` 时 `/v1` 会 fail closed。
> 若把 `AUTH_TOKENS` 误设为代理 API key，上游会返回 `401 Invalid API key`，
> 此时代理本身健康，只是无法用该 token 创建会话。

## 部署步骤

1. 推送仓库（Freebuff 托管从关联仓库构建）。
2. 打开 **Deployments** 面板执行首次 **Deploy**——托管检测到 Next.js
   应用，自动执行 `next build` 并托管到项目域名（首次之后可用
   `freebuff-deploy start` 重新部署）。
3. （可选）在部署环境设置 `AUTH_TOKENS`（Deployments → env）以提供共享
   token 池。不设置站点也能工作：访客在页面上登录后获得各自的 `sk-fb-…`
   key。建议同时设置固定值 `PROXY_SECRET`，让网页登录的 key 跨重新部署
   保持有效。
4. 验证：

```bash
# 健康检查（公开）
curl https://open.freebuff.app/healthz

# 模型列表（需鉴权）
curl https://open.freebuff.app/v1/models \
  -H "Authorization: Bearer <你的显式 API Key>"

# 聊天（流式）
curl https://open.freebuff.app/v1/chat/completions \
  -H "Authorization: Bearer <你的显式 API Key>" \
  -H "Content-Type: application/json" \
  -d '{"model":"deepseek/deepseek-v4-flash","stream":true,"messages":[{"role":"user","content":"Hello!"}]}'
```

## 行为说明

- **健康检查：** `/healthz` 始终公开且仅返回存活状态，不暴露账号 ID、token
  片段、队列状态或模型注册详情。托管网页登录模式可以不配置 `AUTH_TOKENS`；
  共享 token 池或独立 CLI 仍需要 `AUTH_TOKENS`（或已保存的
  CLI 凭证）。如果运行时无法建立可用处理器，`/healthz` 返回
  `200 {ok:false, configured:false}`，其它代理端点返回明确原因的 503。
- **CORS：** `/v1/*` 开放（预检返回 `204`），浏览器客户端可直接调用。
- **流式：** SSE 透传；chat 路由允许长连接（max duration 300 s）。
- **账号限制不变：** 每个账号同一时间只有一个免费会话（约 1 小时），且
  锁定单一模型；会话被占用时请求其它模型返回 `409 model_locked` 并附上
  锁定模型名（代理不会把它掩盖成 503）。
- **状态：** 会话池 / run 管理器 / 模型注册表常驻服务器进程；冷启动
  （重新部署）时惰性重建。API Key 吊销状态同样只在当前进程内有效；如需跨
  实例持久吊销，必须接入共享状态存储。
- **扩展：** 单账号 = 单并发会话，因此托管端点同一时刻服务一个模型；
  在部署环境配置多个 `AUTH_TOKENS` 可让代理在多个账号间轮换。

## 托管应用本地开发

```bash
bun run dev:web    # next dev —— 同一套 /v1 接口 + 落地控制台
bun run build:web  # next build —— 托管构建的产物
```

**Preview 命令（Freebuff Cloud 云 Agent）：** 开发/预览命令设置为

```bash
bun run dev -- -H 0.0.0.0
```

这条命令让 Next.js 开发服务器绑定全部网卡，云预览才能访问；省略 `-p`
时自动使用 Freebuff 注入的 `PORT`（不要传 `-p`，也不要使用裸 `-`
参数——`next dev` 会把它们当作项目目录并报错）。

CLI 服务器不受影响：`bun run dev:cli`（或 `bun run start`）。package 的 `dev` 别名也是 Next.js 应用；独立代理请使用 `dev:cli`。
